# Phase 3 — Real Semantic Embeddings

MATCH only. Qualification, offer construction, Pareto, merchant
economics, Arena strategies, and LEARN were not changed.

## Before

- Provider: `hashing` (`hashing-vectorizer-384`)
- Dimension: 384
- Persistence: Postgres JSONB `variant_embeddings`
- Document version: `product_semantic.v1`
- Phase 1 hero rerank top 5: Sonic Cabin 32 0.8202, Atlas Cabin 72
  0.8195, Nova Fold 19 0.7829, Sonic Sport 38 0.7818, Nova Fold 19
  0.7809
- Phase 1 warm MATCH median: 14.49 ms
- Phase 1 frozen eval (77 queries / 32 with relevance): astraos
  Recall@10 0.1042, NDCG@10 0.9823, hard-constraint violations 0

## After

- Requested provider: `sentence_transformer`
- Model: `BAAI/bge-small-en-v1.5`
- Dimension: 384
- Index version: model `BAAI/bge-small-en-v1.5` + document
  `product_semantic.v1` + SHA-256 `document_hash`
- Indexed documents: 332 / 332 active variants
- Hashing remains the fallback and the CI/unit-test provider

## Architecture

```
ShoppingIntent
        ↓
IntentSemanticProfile (intent_semantic.v1)
        ↓
same embedding model as product documents
        ↓
DETERMINISTIC QUALIFICATION  (unchanged)
        ↓
ELIGIBLE PRODUCTS ONLY
        ↓
cosine similarity
        ↓
existing grounded reranker (weights unchanged)
        ↓
RankedProductMatch
```

`EmbeddingProvider` is a protocol. Primary:
`SentenceTransformerEmbeddingProvider`. Fallback:
`HashingEmbeddingProvider`. Provider-specific ML stays inside
`embeddings.py`.

Vectors stay in Postgres JSONB. No pgvector, Pinecone, or other hosted
index. ~332 variants do not need a distributed vector database.

Hard eligibility always runs first. Dimension or model mismatch skips
or rebuilds a vector. Hash vectors are never reused as semantic
vectors because `embedding_model` must match.

## Product Semantic Documents

`product_semantic.v1` is unchanged in spirit: merchant facts only.

```
Product: Sonic Cabin 32
Brand: …
Category: wireless over-ear headphones
Verified facts:
- active noise cancellation
- 79-hour battery
- 230g
- foldable
Use-case representation: Lightweight ANC headphones suited to
long-duration travel, extended wear, portable use.
```

Use-case lines are templates over present facts. No buyer language, no
utility scores, no Arena outcomes, no invented luxury claims.

Refresh uses `document_hash = sha256(canonical text)`. Same model +
same hash → reuse. Changed facts → re-embed.

## Intent Semantic Profiles

`intent_semantic.v1` still embeds context, outcomes, soft preferences,
values, and trade-offs. Hard constraints stay out of the query text
and continue to be enforced by qualification.

Example:

```
Long-haul travel.
Extended continuous use.
Comfort high.
Reliability high.
Comfort is more important than minimum price.
```

## Model choice

`BAAI/bge-small-en-v1.5` is the production default.

- Retrieval-trained English sentence embeddings
- 384 dimensions (same width as hashing, different space)
- ~33M parameters, CPU-capable
- Deterministic `model.eval()` inference
- Query prefix:
  `Represent this sentence for searching relevant passages: `
- Documents: no prefix
- `encode(..., normalize_embeddings=True)` then cosine
- Cosine on already-L2-normalized vectors does not apply a second
  learned transform; the extra norm in `cosine_similarity` is a no-op
  for unit vectors

Configured via `SEMANTIC_EMBEDDING_PROVIDER` and
`SEMANTIC_EMBEDDING_MODEL`. Not hardcoded at call sites.

First download: `make embeddings-model`. Runtime uses the Hugging Face
hub cache. Model binaries are not committed.

## Retrieval Evaluation

Frozen set: Phase 1 `EVAL_CASES`, snapshotted as
`apps/api/app/eval/fixtures/retrieval_eval_v1.json`
(`retrieval_eval_v1`, 77 queries, 32 with relevance labels).

Labels are human-authored attribute/grade specs, **not** generated by
the embedding model. Relevant IDs are resolved at eval time after
deterministic qualification against the seed 2026 catalogue.

Those labels are broad. Many queries treat most eligible SKUs as
relevant, so Recall@K is structurally small (same pattern as Phase 1
Recall@10). Precision@1 and NDCG are the honest ranking signals.

| Metric | Hashing | Semantic | Hashing + rerank | Semantic + rerank |
| --- | --- | --- | --- | --- |
| Recall@1 | 0.0105 | 0.0105 | 0.0105 | 0.0105 |
| Recall@3 | 0.0315 | 0.0310 | 0.0307 | 0.0307 |
| Recall@5 | 0.0526 | 0.0520 | 0.0517 | 0.0517 |
| Precision@1 | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| MRR | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| NDCG@3 | 0.9790 | 0.9754 | 0.9767 | 0.9745 |
| NDCG@5 | 0.9786 | 0.9784 | 0.9785 | 0.9777 |
| Constraint violations | 0 | 0 | 0 | 0 |
| Warm MATCH (ms) | 8.26 | — | — | 27.27 |

Semantic + rerank is competitive with hashing + rerank. Recall@K after
rerank is identical. NDCG@5 is 0.0008 lower — not a regression that
justifies retuning labels or rerank weights.

## Top-K stability

Across 32 labelled queries, hashing+rerank vs semantic+rerank:

- Top-1 changed: 90.62%
- Top-3 overlap: 0.2396
- Top-5 overlap: 0.3500

The new model does change rankings. High change is not treated as
automatically good; relevance labels still show every top-1 as
relevant (Precision@1 = 1.0).

## Error Analysis

Representative observations:

- **Coarse labels.** Most eligible products satisfy the attribute
  filters, so Recall@K barely moves even when top-5 SKUs change.
- **Reranker still dominates.** Similarity weight remains 0.15. After
  rerank, hashing and semantic Recall@K match exactly.
- **Raw embedding rank can differ.** `hero_stage3` semantic Recall@5
  on similarity-only was slightly below hashing (0.0656 vs 0.0820);
  the grounded reranker recovered the labelled set.
- **No hard-constraint leakage.** Violation rate 0 on both providers.
- **No invented claims.** Documents still omit unsupported luxury /
  designer / leather language.
- **Hashing vs neural cosine scale.** Hashing similarities on the
  hero query sit ~0.22–0.31; BGE ~0.61–0.68. Neither is shown as a
  purchase probability.

No cross-encoder or LLM reranker was added. If a later phase wants
sharper embedding measurement, use graded product-ID labels. Do not
change this frozen set after seeing results.

## Memory / runtime

`sentence-transformers` pulls PyTorch (~127 MB wheel) plus the BGE
small checkpoint. Approximate extra process footprint is a few hundred
MB. Docker `api` image still installs the lean extra-less wheel;
without `make embeddings-model` it reports hashing fallback. Local
demo of Postgres + FastAPI + BGE + Next.js remains reasonable on a
developer laptop.

## Fallback

If the model package or cache is missing:

```
provider_requested: sentence_transformer
provider_used: hashing
fallback_used: true
fallback_reason: model_unavailable
```

Not silent. `/ready` includes `semantic_retrieval` metadata without
running inference.

## Remaining Limitations

- Frozen labels are attribute filters, not graded product IDs, so
  Recall@K understates ranking differences.
- Product documents still include numeric comfort/travel scores from
  the catalogue; those are merchant facts, not buyer copy.
- Rerank coefficients were not retuned (by design).
- Default Docker image does not bundle torch.
- No cross-encoder. Not justified by this eval.

## Recommendation

Phase 3 default for demo/competition:

`SEMANTIC_EMBEDDING_PROVIDER=sentence_transformer`

`SEMANTIC_EMBEDDING_MODEL=BAAI/bge-small-en-v1.5`

Because:

1. Retrieval metrics are competitive with the hashing baseline
2. Hard-constraint violation rate is 0
3. Warm MATCH latency stays interactive
4. The model runs locally from cache after `make embeddings-model`

CI and unit tests keep `SEMANTIC_EMBEDDING_PROVIDER=hashing`.
